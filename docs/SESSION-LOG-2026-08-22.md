## 2) ما نُفّذ في هذه الجلسة — تسلسلي مع الأدلة

### 2.1 ب3 — إعادة تشغيل قابلية التشخيص في وضع QUIC (`e293419`)
**المشكلة:** `/peer` فارغ وlastSeen متجمد في وضع QUIC (PeerManager و
touch_member_last_seen غير موصولين) → تدهور ظهور الحالة في ZTNET.
**التنفيذ:**
- NodeAnnounce → تسجيل فوري في PeerManager + touch_member_last_seen.
- Datagram presence refresh مُقيَّد 5s/نظير (خريطة last_presence داخل حلقة
  الأحداث — لا ضغط على مسار حزم اللعبة).
- RTT prober كل 10s عبر control streams: Ping يحمل sent_ms، Pong يقيس عند
  المرسل (receipt_now − sent_ms) → latency حقيقي في /peer.
- NAT raw-UDP worker محصور بالوضع القديم (في QUIC: keep-alive مدمج 5s +
  probes تؤدي الدور).
**الدليل:** B1-PASS + /peer من الطرفين يعرضان النظير الفعلي بمسار حي.

### 2.2 أ3 — ربط هوية QUIC تشفيرياً (`ea608be` + `7c41282` docs)
**المشكلة:** SkipServerVerification + NodeAnnounce غير مُتحقق = نافذة MITM.
**التصميم المختار:** مصافحة تحدي/إثبات بطبقة التطبيق بدل pinning شهادة TLS —
أقوى عملياً: يربط عنوان ZeroTier بمفتاح تتحكم به العقدة نفسها بلا PKI.
**البروتوكول:**
1. المُعلن يرسل NodeAnnounce{address, public_identity}.
2. المستقبل يرفض الثقة ويصدر NodeChallenge{nonce}.
3. المُعلن يوقع `material = "ZG1" || nonce_be || address` بمفتاحه السري ويرسل
   AnnounceProof{nonce, address, signature, public_identity}.
4. المستقبل: public_identity يُحلل ويجب أن يشتق بالضبط العنوان المعلن، ثم
   تحقق Ed25519 → عند النجاح فقط: remember_announce + حضور + عضوية.
**مصفوفة اختبارات سلبية:** nonce خاطئ، عنوان/مفتاح غير متطابقين، مفتاح آخر،
بلا تحدٍّ صادر — كلها مرفوضة (quic::tests::test_announce_challenge_proof_matrix).
**الدليل الحي:** سجل zg-a يظهر "challenging (أ3)" → "proven"؛ وطلب تكوين وصل
قبل الإثبات **رُفض فعلياً** ("before proven announce — ignored").

### 2.3 ب2 — L2 learning switch وتوجيه انتقائي (`3cf9524`)
**المشكلة:** كل إطار صادر كان يُغرق لكل الأقران — O(N) لكل حزمة.
**التنفيذ:** وحدة `l2_switch.rs`: تعلّم رجعي (src MAC ↔ النقطة الموصِلة)،
أحدث endpoint يفوز عند التجوال، إخلاء بعد 5 دقائق صمت (مربوط بمسبار RTT).
مسار الإرسال: dst MAC معروف → unicast للمالك فقط؛ broadcast/multicast/مجهول
→ flood (ضروري لـARP واكتشاف خوادم الألعاب). جدول واحد مشترك بين
TUN-reader/QUIC-events/relay/prober.
**الاختبارات:** 6 وحدات (تعلم/حل/تجوال/إخلاء/تحليل Ethernet/كشف bcast-mcast).
**الدليل الحي:** B1-PASS بثنائية ب2 (دورة ARP-broadcast ثم unicast كاملة).

### 2.4 ب4 — التعافي وإعادة الاتصال (`0b825a3`)
**المشكلة الجذرية المكتشفة:** اتصال ميت كان **يحتجز فتحة النظير** — أي طلب
اتصال جديد من نظير عاد كان يُرفض بصمت حتى ينتهي كشف الفقد الافتراضي (~40s).
**حزمة الإصلاح:**
- max_idle_timeout 15s على الطرفين (كان افتراضياً ~40s) + keep-alive 5s.
- activate(): الاتصال الجديد الناجح **يستبدل** القديم دائماً ويغلقه برمجياً؛
  حارس stable_id يمنع تنظيفاً خاطئاً من قارئات القديم.
- Disconnected الحقيقي → إخلاء MACs المتعلمة للنقطة (رجوع للflood حتى العودة).
- ترتيب الأهداف: المثبتة (المشغل) أولاً ثم جذور المحلل، إزالة تكرار.
- إرسال متوازٍ لكل الأهداف (كان تسلسلياً: هدف ميت = 5s لكل دورة).
- نبضة تكيفية: 500ms ما دامت هناك شبكة غير OK، ثم 3s استقراراً.
**الدليل الحي:** docker restart zg-b (هوية محفوظة) → **join→ping 2.1s** ✅
(معيار القبول ≤5s). ملاحظة قياس: من لحظة restart الخام تُضاف ~11-14s مهلة
إيقاف docker نفسها — خارج نطاق المنتج.

### 2.5 `idtool validate` + إصلاح rc (`21b38bb`)
**المشكلة (عابر للمستودعين، اكتُشفت بالتحقق الحي):** محرك B1 يستدعي
`idtool validate` ويفتش "is a valid identity" — لكن zgalaxy-rs لم يكن يملك
الأمر → بعد نشر الثنائية الجديدة سيعيد كل تحقق MISMATCH كاذباً. كذلك أخطاء
الاستخدام عبر argv0 كانت تخرج rc=0 صامتة.
**التنفيذ:** أمر Validate أصلي: تحليل + roundtrip توقيع عند وجود السر + فحص
اشتقاق كامل للمفاتيح 32B الأصلية؛ المخرجات التعاقدية وrc=2 لسوء الاستخدام.

### 2.7 أ1-in-QUIC — فرض توكن العضوية (`d662bfc`) — آخر بوابة أمان
**المشكلة:** التوكن كان يُرسل من العميل لكنه **مُهمل** في معالج الطلب
(`token: _`) و**لا يُصدَر** في الاستجابة إطلاقاً.
**التنفيذ:**
- عضو مفوض → استجابة التكوين تضم membershipToken موقّعاً جديداً (TTL 3600s).
- توكن **مُقدَّم** غير صالح (توقيع/عضو/شبكة/انتهاء/مراجعة) → رفض الطلب مع
  تحذير — سحب التفويض يسري خلال TTL بدل إعادة تسليح النظير.
- رصد: membershipToken ظاهر في GET /network (كان غائباً من network_to_zt_json).
**الدليل الحي القاطع:** B يحمل توكن موقّعاً ظاهراً عبر /network بمطابقة بنية
أ1 الكاملة `{c,e,m,n,r,t}` (مفكوكاً موثقاً أدناه)، B1-PASS، وصفر رفضات خاطئة
عبر دورات تحقق متتالية.

**التوكن الحي المفكوك (من /network على zg-b):**

## 8) قرارات تصميم موثقة (لماذا هكذا)

| القرار | السبب |
|---|---|
| QUIC Datagrams للبيانات + Streams للتحكم | بلا head-of-line blocking — دلالات NIC حقيقي للألعاب؛ موثوقية للتحكم |
| تحدي/إثبات بطبقة التطبيق بدل pinning TLS | يربط عنوان ZeroTier بمفتاح العقدة نفسها بلا PKI؛ SkipServerVerification يبقى مقبولاً لأن الهوية مثبتة فوق TLS |
| TAP L2 (لا L3 TUN) | ARP/broadcast/اكتشاف خوادم LAN يعبر الشبكة الافتراضية |
| MTU 1186 في QUIC | 1200 − 14 رأس Ethernet — بلا إسقاط صامت |
| MAC حتمي SHA-256(node,nwid) | استقرار عبر إعادة التشغيل وتمييز بين العقد |
| membership token TTL 3600s + ربط revision | سحب التفويض يسري؛ تغيير التكوين يبطل القديم |
| replace-on-dial للاتصالات | الاتصال الميت لا يحتجز الفتحة (جذر تعافٍ 40s) |
| نبضة تكيفية 500ms/3s | تعافٍ ≤5s دون استنزاف دائم |
| unicast بالتعلّم + flood للبث فقط | O(1) للحزمة unicast؛ ARP/اكتشاف الألعاب يعمل |
